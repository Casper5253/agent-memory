Coding agents that remember where the project stands

Every new coding-agent session starts from zero. We built AgentMem so that each one opens already knowing the project's current state, cited to the sessions that established it. The hard part was not storing memory. It was keeping the current state honest.

October 202612 min readWindows 11 · Claude Code · Codex · OpenCode · Obsidian

We run three coding agents side by side: Claude Code, Codex and OpenCode. The companion piece, Herding three coding agents on one budget, covers how they split work. This one is about what they share across time. A decision made with one agent on Monday should still be known to a different agent on Tuesday, without anyone pasting it in.

The obvious answer is to save the sessions and search them. We did that first. It turned out that saving is easy, and that most of the work is in deciding what counts as true right now.

First, the moving parts

Session note

One Markdown note per working session, written by a background worker after the session ends. It holds a short summary and numbered evidence entries, each quoting the transcript. Session notes are history and are never edited.

Status page

One page per project with seven fixed sections: purpose, what works, latest progress, active work, open questions, key decisions and next steps. It is the only place that says what is true now.

History

A per-project file that keeps every item that left the status page, with the reason it left and the evidence that replaced it. Search labels it, and the session notes, as historical.

Version one looked fine and was not

The first version captured every session from all three agents, summarized it with a small model, and rewrote a project note from the summaries. Search worked, and unit tests passed. Then we stopped asking whether the parts worked and asked a different question. Does a brand-new session actually start with an accurate picture? We ran real agents through a scripted lifecycle (decide, end, resume, reverse a decision, get killed) and scored what the next session received.

It did badly:

  • Most work never reached the project note. Updates over 8,000 characters were parked and never drained. 92 of 213 captured sessions never reached the project state.
  • The summarizer invented facts. It treated its own temporary directory as a project fact, and the next session repeated it.
  • Shell work was invisible. The quality gate counted only edits made through the agent's file tools. A Codex session that changed files and committed with shell commands was skipped. Its decision was lost, and a later session inherited a decision that had already been reversed.
  • Folders became projects. Every git worktree an agent worked in became a new fragment project. The team's own task branches created ten of them.

A detour through a knowledge wiki

Our first plan for the fix came from Andrej Karpathy's LLM Wiki. The idea is to stop retrieving from raw documents on every question, as typical RAG does. Instead, the model builds and maintains a persistent, interlinked Markdown wiki, so knowledge is compiled once and kept current. It has three layers: immutable raw sources, a wiki that the model owns, and a schema file (such as AGENTS.md) that tells the model how to maintain it. The model ingests new sources, answers queries with citations, and periodically lints the wiki for contradictions and stale claims.

We built a version of it for AgentMem: a project claim store of about 2,600 lines, with evidence-linked claims and explicit decision succession. We evaluated it carefully. On a sealed set of synthetic questions it answered 34 of 83, where the old search answered none.

Two things stopped us from adopting it as a second store. On 36 questions built from the git history of real repositories, the improved plain search was level with it or ahead: 10 wins to 7, with 11 ties, in a partial rerun. And it failed its own safety gate. In 5 cases it presented a superseded fact as current, which is the exact failure the project existed to remove.

The deeper problem was the question itself. Those tests asked whether memory can answer a question. Our real use is different. A new session needs the current state pushed to it before anyone asks anything. The store won the question tests while the page that sessions actually read kept falling behind.

In the end we kept the wiki's core and dropped the second store. The session transcripts and notes are the immutable raw sources. Each project's status page is a small wiki page that the model maintains, compiled once and kept current. The vault's AGENTS.md is the schema. The one change is to the lint step. In AgentMem, the checks for contradictions, stale claims and unsupported statements do not run as a periodic pass by the model. Code enforces them on every update, as the next sections describe. The claim store stays in the code, switched off.

The evaluation measured the system we were building, not the job we needed done.

How a session becomes current state

  1. StartThe hook finds the project, from the repository root or the parent of a worktree, and injects its status page.
  2. CaptureAfter each turn, a hook queues a small job. A detached worker reads the transcript from where the last capture ended.
  3. SummarizeA small model writes the summary. Every claim must quote the digest, and specifics such as paths, hashes and numbers must appear in it.
  4. ReconcileThe page is locked and re-read. The model proposes what to keep, add and retire. Code checks every proposal against fixed rules.
  5. RetireRetired items move to the project's history with their reason. The page and the history are written through a journal, so a crash finishes cleanly.

Code decides what may leave the page

The model is good at reading a session and proposing an update. It is not reliable at enforcing rules: the rules we left to the prompt alone broke in live runs. So the model proposes, and code decides:

  • Evidence or nothing. A new item must cite an evidence anchor from the session note, and its wording must match the quoted text. Uncited summaries never change the page.
  • Like replaces like. Only a newer decision can retire a decision. Only a next step, open question or active item can replace one of those. A side door through which a decision could be moved into "next steps" and then retired was found in review and closed.
  • Newer evidence wins. Each item remembers when its evidence was recorded. A session that started earlier but finished later can still add what it learned, but it cannot retire anything newer.
  • No silent no-ops. An update that adds nothing is logged and stays visibly pending; it is never counted as done. One bad item no longer blocks the good ones.
  • No omitted decisions. If the summary contains a cited decision and the model leaves it out, code adds it, subject to the same rules.
  • Project facts only. "Waiting for review" and "a test run is in progress" are agent process, not project state. Code refuses them.
  • Git is read live. Branch, HEAD and working-tree state are read at session start and never stored, so they cannot go stale.

Tests passed. Live runs failed.

By the end the suite had 607 tests, and it passed at nearly every step. It still missed each defect below. Each was found by running real agents against the real vault and inspecting what the next session received:

  • Short turns were never captured. A turn judged trivial moved the capture cursor past its content, so a session made of short discussion turns was judged one turn at a time and never saved. This was probably losing discussion-only sessions all along.
  • A model left out a decision it was given. The summary held the decision with citations. The update omitted it, and nothing noticed.
  • One weak question blocked a valid decision. All-or-nothing validation rejected a whole update because one open question lacked support.
  • Search called current text unverified. The search index cut snippets with an ellipsis, so the check that a hit is still on the page always failed.
  • Startup could show nothing. When the first item of every section did not fit together, the startup package fell back to no items at all.

Each fix came with a test that fails on the old code. But the tests came after the live runs, not before. Hundreds of passing unit tests did not demonstrate the product, and adjusting a test to match new behaviour twice hid a real defect. A small, fixed contract of ten observable criteria, checked live, did more than test volume.

What it still does not do

OpenCode support rests on the shared pipeline and tests; it was not verified live in this release. A session killed before its first turn finishes is recovered only when a later hook or worker run notices it. The 112 captures from before citations were required stay visible as backlog but cannot update a page. Status items longer than 280 characters are left out of the startup package, with a pointer to the full page. These are documented and deferred until normal use shows they matter.

What we would tell ourselves at the start

  • Test the job, not the parts. The question was never "can memory answer this?" It was "does a new session start with the truth?"
  • Let the model propose and code dispose. Every invariant that mattered ended up in code.
  • Evidence beats summaries. Requiring each claim to quote its source removed invented facts without making summaries worse.
  • One authority for now. A second store that also states current facts creates a second truth. Keep history searchable, and keep "current" in one place.
  • Run it live early. Every live run found something the suite had missed.

AgentMem is a few thousand lines of standard-library Python with a QMD search index and an Obsidian vault. It has 607 tests and runs on Windows 11 with Claude Code, Codex and OpenCode. The numbers come from the project's decision log and its live acceptance runs.
